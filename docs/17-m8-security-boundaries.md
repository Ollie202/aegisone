# M8 Security Boundaries — Discovery, Source Auth, and Verification

## Scope

M8 adds internet-facing discovery and publisher authentication around a secret-bearing verification system. This document defines the minimum controls required before the backend is considered frontend-ready.

The existing `docs/07-security-threat-model.md` remains authoritative for M1–M7 threats. M8 adds new attack surfaces; do not weaken existing mitigations.

## New trust boundaries

```text
untrusted search query
      |
      v
proofrail-app
      |
      +--> third-party discovery APIs (untrusted data)
      |
      +--> GitHub OAuth / repository metadata
      |
      +--> Supabase mutable catalog
      |
      v
internal authorization boundary
      |
      v
proofrail-worker
      |
      +--> exact GitHub source acquisition
      +--> bounded Skill package handling
      +--> 0G Sandbox / Storage / registry
```

Every arrow is a validation boundary.

## Threat M8-001 — discovery metadata masquerades as proof

**Attack:** upstream ARD provider returns fields such as `verified`, `trusted`, `trustManifest`, source repo, or high relevance and AegisOne displays/uses them as AegisOne evidence.

**Mitigation:**

- all upstream data maps only to discovery/provider metadata;
- only validated AegisOne evidence model can populate AegisOne trust dimensions;
- namespaced AegisOne metadata is generated by AegisOne, never copied blindly from upstream;
- regression tests assert round-trip of `INDEXED` resources cannot become `MATCH`/authenticated.

## Threat M8-002 — discovery prompt/description manipulation

**Attack:** malicious resource description attempts to manipulate an LLM consumer into selecting/installing it.

**Mitigation:**

- AegisOne search API treats descriptions as untrusted text;
- no server-side LLM interprets them for trust decisions;
- agent MCP responses mark relevance as discovery-only;
- no automatic installation/execution;
- consuming-agent instructions must preserve user choice.

## Threat M8-003 — SSRF from arbitrary resource URLs

**Attack:** attacker supplies URLs pointing to localhost, Railway metadata/internal services, cloud metadata, private IPs, or redirect chains.

**MVP rule:** avoid generic server-side URL fetching wherever possible. Provider adapters call fixed allowlisted upstream origins. GitHub source acquisition uses parsed GitHub owner/repo identifiers rather than arbitrary fetch URLs.

Where resource/distribution download is required:

- HTTPS only;
- scheme allowlist;
- host validation;
- DNS resolution checks against loopback/private/link-local/reserved addresses;
- re-check resolved target after redirects;
- redirect limit <= 3;
- block URL credentials/userinfo;
- block nonstandard ports unless explicitly allowlisted;
- total timeout;
- connect/read deadlines;
- response-size cap;
- content type is advisory, not trusted;
- never forward internal bearer tokens/OAuth tokens to redirected hosts.

Blocked address classes must include at least IPv4/IPv6 loopback, RFC1918/private, link-local, unique-local IPv6, unspecified, multicast and cloud metadata targets.

## Threat M8-004 — zip/tar/archive bombs and path traversal

Agent Skills may contain multiple files/resources.

Before extraction/canonical packaging enforce:

- maximum compressed bytes;
- maximum decompressed bytes;
- maximum file count;
- maximum per-file bytes;
- normalized relative paths only;
- reject absolute paths;
- reject `..` traversal after normalization;
- reject duplicate normalized paths;
- reject symlink/hardlink escape behavior unless the existing Skill format explicitly defines safe handling;
- reject special device/FIFO entries;
- extraction inside a fresh bounded temporary directory;
- cleanup on all success/failure paths.

Reuse existing M7 package protections wherever possible.

## Threat M8-005 — verification spend abuse

**Attack:** anonymous user repeatedly triggers 0G Sandbox/Storage/registry work.

**Mitigation:**

- public search/inspect/policy endpoints are read-only/cheap;
- expensive verification route is not anonymous;
- source claim creation/authentication alone does not automatically spend 0G;
- verification jobs require server-side authorization and explicit supported artifact family;
- rate limit by authenticated claim/user/session plus global concurrency caps;
- hard per-job budget/deposit caps;
- queue jobs, don't spawn unlimited concurrent sandboxes;
- no generic public `/verify-any-url` endpoint.

## Threat M8-006 — signer/key exposure

Current production separation is correct:

- `proofrail-app` must not contain `ZEROG_STORAGE_PRIVATE_KEY`;
- `proofrail-worker` owns secret-bearing 0G operations;
- frontend/browser never receives signer material;
- environment variable names/values never appear in diagnostics responses;
- worker health may state signer configured as a boolean but never reveal key material.

Any future app-to-worker token must be independent from Supabase/GitHub/0G secrets.

## Threat M8-007 — GitHub OAuth CSRF/replay

Required controls:

- random 128+ bit state nonce;
- bind callback to same browser session;
- 5–10 minute state expiry;
- state single use;
- `Secure`, `HttpOnly`, appropriate `SameSite` cookie;
- exact callback URL allowlist;
- validate `returnTo` against local allowlist/path only;
- authorization code exchanged once server-side;
- token/code never logged.

## Threat M8-008 — fake source authority

**Attack:** user points AegisOne to a repository they can only read or do not control.

**Mitigation:**

- `DECLARED` by default;
- require real GitHub App user authorization for authentication upgrade;
- inspect stable repository ID and effective repository permissions;
- only effective write/push/admin-equivalent access earns `REPOSITORY_AUTHENTICATED`;
- read/triage/unknown => no upgrade;
- record authenticated GitHub user ID, repo ID, permission and timestamp in evidence;
- exact commit independently resolved.

## Threat M8-009 — repo rename/transfer and identity confusion

Use stable GitHub numeric repository ID and owner/user IDs as observed evidence in addition to human-readable names.

A renamed repo does not mutate historical source-claim evidence. A transfer/new ownership context should be surfaced during current re-checks rather than silently rewriting old claims.

## Threat M8-010 — authenticated account compromise

Repository authentication proves repository authority at a point in time, not benign intent or uncompromised identity.

Mitigations/communication:

- do not call `REPOSITORY_AUTHENTICATED` trusted/safe;
- separate security audit;
- support stronger signed provenance when available;
- later source governance/multi-party identity can be added without changing correspondence semantics.

## Threat M8-011 — attestation presence mistaken for attestation verification

**Attack/bug:** REST API returns an attestation bundle and AegisOne emits `SIGNED_RELEASE` without signature/identity verification.

**Mitigation:**

- candidate listing and cryptographic verification are separate code paths/states;
- use GitHub-supported `gh attestation verify` or an equivalently reviewed verifier;
- constrain expected repository/source digest and signer identity as policy requires;
- failed/unavailable verification => no `SIGNED_RELEASE`;
- retain verifier output/evidence reference without treating arbitrary JSON as authoritative.

## Threat M8-012 — source claim mutation in Supabase

Supabase is mutable.

Controls:

- canonical source claim has deterministic digest;
- application recomputes/verifies digest before presentation/use;
- authenticated source observation preserved historically;
- completed verification commits source claim digest into canonical AegisOne evidence/0G commitment where applicable;
- new claim supersedes rather than overwrites old canonical claim.

## Threat M8-013 — stale evidence silently treated as current

Store/expose:

- `observedAt` for discovery;
- `authenticatedAt` for source authority;
- `verifiedAt` for canonical evidence;
- explicit stale/age policy.

Consumer policy may require a maximum evidence age. Missing/invalid time fails closed according to the policy's missing-evidence setting.

## Threat M8-014 — provider outage causes false negative/positive trust

Discovery provider outage is availability state only.

- isolate provider failures;
- return partial results where useful;
- record provider failure separately;
- never downgrade existing canonical AegisOne evidence because search provider is offline;
- never mark unreturned resources malicious/untrusted merely because provider stopped returning them.

## Threat M8-015 — response amplification / resource exhaustion

Public API limits:

- body max ~32 KiB for ARD search;
- query length max 2,000 chars;
- max page size 25;
- bounded provider concurrency;
- max upstream response ~1 MiB/provider for MVP;
- request total deadline ~5 seconds;
- bounded JSON serialization/result metadata;
- simple IP/session rate limit as traffic requires;
- do not reflect massive upstream raw objects to caller.

## Threat M8-016 — arbitrary shell execution from source metadata

Never construct shell commands by concatenating untrusted repository paths, tags, filenames, workflow names, or query content.

- use structured argument arrays with `spawn`/equivalent;
- validate commit SHA format;
- constrain supported Skill build/package path;
- no caller-supplied install/build command in open M8 Skill verification;
- existing build recipes remain explicit/constrained.

## Threat M8-017 — unsafe GitHub CLI attestation invocation

If using `gh` in the worker:

- pin/record tested `gh` version;
- use argument arrays, not shell interpolation;
- place artifact in bounded temp path generated by worker;
- expected repo and source digest come from validated claim, not raw command text;
- command timeout;
- cap stdout/stderr bytes;
- parse `--format json` strictly;
- scrub bearer tokens from child process environment unless required;
- never return raw stderr containing credentials.

## Threat M8-018 — MCP becomes a privileged backdoor

M8 MCP server is a read/policy convenience only.

Allowed initial tools:

```text
aegisone_search
aegisone_inspect
aegisone_evaluate
```

Not allowed initially:

```text
aegisone_install
aegisone_execute
aegisone_sign
aegisone_run_arbitrary_build
aegisone_upload_secret
```

MCP tool handlers call the same validated application services as REST.

## Threat M8-019 — security audit overclaim

Static Skill audit is deterministic but incomplete.

- report findings/rules/severity;
- absence of findings is not proof of safety;
- `MATCH` and audit remain independent;
- LLM advisory remains non-authoritative if added later.

## Threat M8-020 — frontend trust confusion

Although M9 frontend is later, backend contracts must make misleading UI difficult.

Do not expose one ambiguous boolean such as:

```json
{"verified": true}
```

without independent dimensions.

Frontend-facing JSON must expose named evidence states so the UI can render:

- Indexed
- Source authenticated
- Source inspected
- MATCH/MISMATCH/insufficient evidence
- audit severity/findings
- evidence age/storage/registry pointers

## Worker job limits

Codex should centralize policy constants rather than scatter them across handlers.

Recommended M8 starting limits (adjust only with evidence/tests):

```text
max source archive download:       25 MiB
max Skill package decompressed:    20 MiB
max individual Skill file:          5 MiB
max Skill files:                  500
max public search body:             32 KiB
max public search page size:        25
provider HTTP timeout:               3 s
whole search deadline:               5 s
max redirects for distribution:      3
verification concurrency:            1–2 on current budget
```

If existing repository limits are stricter, keep the stricter value unless the issue explicitly requires expansion.

## Security test matrix

Every M8 package/route should add applicable tests for:

- malformed JSON;
- oversized body;
- invalid URL scheme;
- private/loopback target;
- redirect to private target;
- invalid commit SHA;
- read-only GitHub authority;
- OAuth state mismatch/replay;
- stale evidence;
- provider timeout;
- provider malformed response;
- duplicate discovery result;
- archive traversal;
- duplicate archive path;
- too many files;
- decompression/size limit;
- `MATCH` without both digests rejected;
- metadata claiming `MATCH` ignored;
- DB-only trust escalation rejected;
- MCP cannot invoke privileged operations.

## Operational pre-frontend security gate

Before M9 frontend starts:

- [ ] Gitleaks full-history/PR check green;
- [ ] complete `pnpm check` / `pnpm test` green;
- [ ] Supabase RLS/security advisor reviewed after M8 migrations;
- [ ] `proofrail-app` variable list contains no 0G private key;
- [ ] `proofrail-worker` has no anonymous mutation endpoint;
- [ ] GitHub OAuth secrets only on app service;
- [ ] public search cannot trigger live 0G spend;
- [ ] SSRF and package limits covered by tests;
- [ ] source-auth downgrade/read-only tests green;
- [ ] canonical evidence integrity checks still guard cached verdicts;
- [ ] one controlled substitution end-to-end run produces expected `MISMATCH` without weakening any labels.
